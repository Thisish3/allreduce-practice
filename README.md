# allreduce 알고리즘 직접 구현 (C, pthreads)

텐서 병렬 LLM 추론은 레이어마다 **allreduce**를 호출합니다. 여러 장치가 각자 계산한 부분 결과를
원소별로 합쳐 모두가 같은 결과를 갖게 하는 연산이고, NCCL의 핵심입니다. 이 저장소는 그 알고리즘 세 가지를
C로 직접 구현하고, **어떤 메시지 크기에서 어떤 알고리즘이 이기는지**를 통신량 이론과 실측으로 비교합니다.

## 구조

```
src/comm.[ch]       장치 N개 = 스레드 N개, 링크 = (src→dst) 방향별 1슬롯 메일박스
                    send/recv/barrier + rank별 송신 바이트·메시지 카운터
src/allreduce.[ch]  naive / ring / recursive doubling
src/runner.[ch]     rank마다 스레드를 띄워 반복 실행하는 하네스
tests/              정확성(96케이스) + 통신량이 이론식과 일치하는지 검증
bench/              메시지 크기별 지연, NCCL 방식 busbw
```

## 세 알고리즘과 비용 모델

N = rank 수, S = 버퍼 크기, α = 메시지당 고정 지연, β = 링크 대역폭

| 알고리즘 | 방식 | 단계 수 (α 비용) | rank당 송신량 (β 비용) |
|---|---|---|---|
| naive | 모두 rank 0으로 모아 더한 뒤 다시 뿌림 | 2 (단, rank 0이 N-1개를 순차 처리) | rank 0만 **(N-1)·S** → 병목 |
| ring | reduce-scatter + all-gather, 버퍼를 N조각으로 나눠 링으로 돌림 | **2(N-1)** | **2(N-1)/N · S** ≈ 2S, N과 무관 → 대역폭 최적 |
| rd (recursive doubling) | 단계마다 거리 2^k인 상대와 전체 버퍼 교환 | **log₂N** → 지연 최적 | log₂N · S |

- **작은 메시지**는 α(단계 수)가 지배합니다 → 단계가 적은 rd/naive 유리
- **큰 메시지**는 β(보내는 양)가 지배합니다 → ring 유리

NCCL이 메시지 크기와 토폴로지에 따라 ring과 tree 알고리즘을 골라 쓰는 이유가 이 트레이드오프입니다.

## 검증

```bash
make test    # 정확성 + 통신량
make tsan    # ThreadSanitizer로 데이터 경합 검사
make bench   # 성능 비교
```

- **정확성**: N ∈ {1,2,3,4,5,8} × 원소 수 ∈ {0, 1, 3, 7, 1000, 4099}. rank 수보다 적거나 N으로 나누어떨어지지 않는
  경계 케이스까지 포함해 96케이스 통과. 입력을 정수값 float로 잡아 덧셈 순서와 무관하게 정확히 비교.
- **통신량**: 카운터로 실제 송신 바이트를 세서 이론식과 **정확히 일치**하는지 테스트
  (ring = 2(N-1)/N·S, naive root = (N-1)·S, rd = log₂N 메시지 × S).
- **ThreadSanitizer**: 경합 없음.

## 실측 (Apple M2, 성능 코어 4 + 효율 코어 4, 20회 중앙값)

N = 8

| 크기 | naive | ring | rd | 가장 빠름 |
|---:|---:|---:|---:|:---:|
| 256B | 63 us | 275 us | **49 us** | rd |
| 16KB | **63 us** | 450 us | 80 us | naive |
| 256KB | **284 us** | 497 us | 339 us | naive |
| 1MB | 1083 us | **917 us** | 1523 us | ring |
| 4MB | 4764 us | **3225 us** | 18345 us | ring |
| 16MB | 39706 us | **36413 us** | 76705 us | ring (근소) |

N = 4에서도 같은 패턴입니다. 64–256KB에서는 rd, 1–4MB에서는 ring이 이기고, ring이 naive보다 최대 2.1배 빠릅니다.

**읽는 법**
1. **작은 메시지에서 ring이 3~7배 느림**: 단계가 14번(2·(8-1))이라, 단계마다 스레드를 깨우는 비용(α ≈ 수십 us)이 14번 쌓입니다.
   rd는 3단계라 가장 빠릅니다. 비용 모델의 α 항이 그대로 보입니다.
2. **1–4MB에서 ring이 역전**: 보내는 양이 지배하기 시작하면 rank당 ~2S만 보내는 ring이 이깁니다.
   rd는 4MB에서 ring보다 5.7배 느립니다. 매 단계 전체 버퍼(S)를 3번 보내기 때문입니다.
3. **crossover 지점**: N=8 기준 256KB와 1MB 사이. 실제 NCCL도 이런 경계에서 알고리즘을 바꿉니다.

## 한계: 공유 메모리 시뮬레이션이라 생기는 왜곡

- **링크가 독립적이지 않음**: 실제 GPU/LPU는 장치마다 전용 링크가 있어서 ring의 모든 링크가 동시에 전속력으로 돕니다.
  여기서는 모든 "링크"가 같은 DRAM을 공유하므로, 16MB(8 rank × 버퍼 + 메일박스 ≈ 수백 MB)에서는 메모리 대역폭이
  병목이 되어 ring의 이점이 거의 사라집니다(N=4, 16MB에서는 naive가 이기기도 함). **대형 메시지 결과는 실제 인터커넥트의
  경향으로 해석하면 안 됩니다.**
- **α가 과장됨**: 실제 NVLink의 메시지 지연은 수 us 수준인데, 여기서는 mutex/condvar 스레드 깨우기라 수십 us입니다.
  그래서 crossover가 실제보다 큰 메시지 쪽으로 밀려 있습니다.
- **메일박스 복사 2회**: 송신 시 복사, 수신 시 복사. 실제 NCCL은 zero-copy/P2P 쓰기를 씁니다.
- **파이프라이닝 없음**: NCCL ring은 조각을 더 잘게 나눠 송신과 덧셈을 겹칩니다. 여기서는 한 단계가 끝나야 다음 단계로 갑니다.

## LPU와의 연결

하이퍼엑셀 LPU 논문(*LPU: A Latency-Optimized and Highly Scalable Processor for Large Language Model Inference*,
arXiv 2408.07326)은 여러 LPU 사이에 **ESL(expandable synchronization link)**을 두어 "LPU 간 데이터 동기화 지연을 숨긴다"고
설명합니다. 이 실습의 용어로 말하면, 추론(디코드)처럼 메시지가 작고 지연이 중요한 구간에서 α 항과 통신 대기 시간을
계산 뒤로 숨기려는 설계입니다. 위 실측에서 작은 메시지가 단계 수(α)에 지배되는 이유가 이런 전용 동기화 링크가
필요한 이유와 같습니다.

## 다음에 해볼 것

- ring 파이프라이닝: 조각을 더 잘게 나눠 송신과 덧셈을 겹치고, 효과를 측정
- α-β 모델 피팅: 실측으로 α, β를 추정해서 crossover 지점을 예측하고 실측과 비교
- 2D/계층 allreduce: 노드 내 ring + 노드 간 tree (NCCL의 멀티노드 방식)
